# 多 Agent 协作工作流现状评估与演进方案

> 日期：2026-08-05
> 性质：架构分析，非实施计划。结论供决策参考，未改动任何代码或流程文件。
> 涉及：`AGENTS.md`「多 Agent 协作工作流」、`docs/ai-workflow/*`

## 0. 数据基线

对本仓库 72 次提交的统计：

| 指标 | 数值 |
|------|------|
| 总提交数 | 72 |
| `docs:` 类提交 | 34（47%） |
| 最近 40 条中 `docs:` 占比 | 27（67.5%） |
| 流程自身维护提交（PLAN / BACKLOG / 模板 / 清空 / 交接） | 27（37.5%） |
| `PLAN.md` 被改动次数 | 29 |
| `feat:` 提交 | 18 |
| 8 月以来提交 | 44 |

**关键事实：流程自身的维护提交（27）超过了功能产出提交（18）。**

这不是流程设计质量问题——四级 review 分级、粗细双模式、TEMPLATE 真相源收敛都是扎实设计。问题是**固定治理成本被摊到了平均 ≤50 行的 micro 任务上**，单位任务的流程税过高。

> 口径注：「最近 40 条」窗口恰与流程密集建设修补期（8 月上旬）重合，属峰值取样而非稳态；稳态仪式提交约每任务 1-3 条。

## 1. 现状本质：人在充当操作系统

将当前工作流按操作系统角色映射：

| OS 角色 | 当前实现 | 评价 |
|---------|----------|------|
| 共享内存 | `PLAN.md`（唯一可写黑板） | 单文件，结构上只能容纳一个任务 |
| IPC / 消息传递 | 人的剪贴板 | 单线程、有延迟、阻塞、不可重放 |
| 调度器 | 人 | 系统时钟就是你本人 |
| 互斥锁 | 「同一文件严格串行」 | 全局 GIL，并行度恒为 1 |
| 交接协议 | `git diff` | **全套里最工业级的一环，应保留** |
| 状态机 | markdown 勾选框 | 人可读、机器不可读 → 自动化的根本障碍 |
| 持久化 | git log + `BACKLOG.md` | PLAN 清空后历史需 git 考古 |

### 1.1 三个结构性缺陷

**缺陷 A：串行是「缺乏隔离原语」的伪装**

「同一文件严格串行」表面是纪律，实质是因为没有工作目录隔离机制。工业标准答案是 `git worktree`：同一仓库 checkout 多个工作目录、各自独立分支、共享 `.git` 对象库，冲突交给 merge 而非人工排班。

缺的不是纪律，是隔离机制。但需加权：本仓库任务重叠度高（多任务触碰同一视图），当前痛点集中在传话 IPC 而非文件锁；worktree 解决并行上限，不直接消灭搬运。

**缺陷 B：规则源已漂移到 7 处**

`AGENTS.md` / `CLAUDE.md` / `CLAUDE.local.md` / `PLAN.md` / `TEMPLATE.md` / `BACKLOG.md` / `~/.claude/commands/codex-plan-exec`

已为此付过一次账：`c25abbe docs: 模板真相源收敛 + AGENTS.md 三处事实修正`。

更严重的是最后一项——**`/codex-plan-exec` 不在仓库内**，位于用户全局目录。仓库自称「唯一事实源」，但最核心的执行器换台机器即失效。

**缺陷 C：2 → N 是架构相变，不是线性加压**

人肉传话链路数 = N(N-1)/2。当前 1 条链路已消耗 37.5% 的提交；3 个 Agent = 3 条链路，人工调度会当场失效。这不是「再加一份文档」能解决的问题。

## 2. 演进路线：四层阶梯，不跳级

| 层 | 名称 | 解决什么 | 代价 | 何时做 |
|----|------|----------|------|--------|
| L0 | 人肉总线 | —（现状） | 并行度 1，不可离场 | — |
| L1 | CLI 直调（仅出站一跳） | 仅自动化「Claude→Codex 启动」；回站 review 仍人工，且此前实测失败 | 前提待解 | 暂缓 |
| L2 | worktree 并行隔离 | 打破全局串行锁 | 半天 + token 涨 2–5 倍 | 需并行时 |
| L3 | 平台调度 | 事件触发、可离场 | 换生态 + 月费 | ≥3 个并行任务时 |

### 2.1 L1 剩余可执行动作（P0 已撤回，见 §2.1.1）

| 优先级 | 动作 | 解决什么 | 预估 |
|--------|------|----------|------|
| P0 | ~~直调 CLI~~ **已撤回**：用户此前已实测「让本命令直接调 `codex` 执行」失败，退回复制提示词。本命令本质是单 Agent 的 prompt 生成器，无编排能力（根因见 §2.1.1）。 | 不解决 | — |
| P1 | PLAN.md 旁挂 `state.json`：`{task_id, phase, round, blocking[]}`。markdown 给人看，JSON 给机器读 | 状态机可查询 → 可编排；**落地时须定读者**（如 `/codex-plan-exec` 读它校验 phase），否则沦为第二个手工同步源 | ~1h |
| P2 | 改为 `tasks/<date>-<slug>.md`，一任务一文件，**不清空、不回填** | 消灭 27 条仪式性提交，历史天然归档 | ~0.5h |
| P3 | `/codex-plan-exec` 移入仓库 `.claude/commands/` | 恢复「唯一事实源」的完整性；注意 `.gitignore` 当前忽略整个 `.claude/`，须加 `!.claude/commands/` 例外，否则名移实不移 | ~0.2h |

### 2.1.1 校正：/codex-plan-exec 不是多 Agent 编排器，且直调 CLI 此前已失败

用户反馈已实测：曾尝试让本命令直接调用 `codex` 执行任务，未成功，才退回「打印 prompt 供复制」的当前形态。据此，原 L1-P0「改命令直调 CLI、干掉两个人工搬运节点」的判断需纠正。

**事实 1：本命令没有任何多 Agent 编排能力。**
- `allowed-tools: Read` —— 它连 Bash 权限都没有，更不可能 spawn 子进程或管理 Agent 花名册。
- 它只做一件事：读 `PLAN.md` 的 TASK_BODY → 套 XML 模板 → 输出一段给「单个 Codex 会话」的 prompt。
- 工作流里所谓的「多 Agent 协作」(Claude + Codex) 完全靠**人在中间当总线**实现：Claude 写计划 → 人复制 → Codex 执行 → 人复制 diff 回 Claude。命令只是出站那一跳的「提示词打印机」，不是调度器。

**事实 2：直调 CLI 即便成功，也只自动化「出站一跳」，回站仍是断的。**
- 出站（Claude→启动 Codex）：理论上 `cmd /c "codex exec --approval-mode full-auto ..."` 能启动一个**无头（headless）Codex 会话**。
- 回站（Codex 完成→Claude review）：斜杠命令在 `codex exec` 返回后即结束，会话不会自动接力做 review。要闭环要么人手动触发，要么让同一个 Claude 既当 launcher 又当 reviewer —— 后者会把 §4 的质量红线（reviewer 必须独立于 implementer）打破。

**事实 3：此前直调失败的真实根因（结合已验证的环境现象）**
1. **sh shim 路径 bug（已实测）**：Git Bash 下 `codex --help` 报 `MODULE_NOT_FOUND: f:\e\Software\...` —— npm 装的 `codex` 是 sh 版 shim，Git Bash 把脚本路径翻成错误盘符。若命令用 Git Bash 跑 `codex`，必挂。需 `cmd /c` 包一层走 `.cmd` shim（CMD 下实测 `codex-cli 0.146.0` 正常）。
2. **无头 vs 桌面端不一致**：`codex exec` 跑的是 headless CLI，与用户习惯的「桌面端 Codex」GUI 是两套执行上下文（认证、沙箱、模型配置可能不同），行为不一致导致「跑起来也不是预期那样」。
3. **审批门悬挂**：不显式加 `--approval-mode full-auto`，Codex 执行命令时会卡在审批门；在非交互管道里直接挂起或报错。
4. **授权/沙箱**：headless 会话的 Codex 需独立配置 OpenAI Codex 凭证与文件系统/网络沙箱权限，桌面端那套不一定继承。

**结论**：不要把「改造这个命令」当成自动化的入口。它天生是单 Agent 中继，改不出多 Agent 编排。要真正消灭两个人工搬运节点，只能走到 L2（worktree + 独立编排脚本）或 L3（平台事件流）——因为那才能同时解决「出站自动启动 + 回站自动通知 + reviewer 角色隔离」三件事。复制提示词在当前约束下反而是合理的 MVP。

### 2.2 L2 触发条件与前置

仅当出现「同时推进 ≥2 个互不依赖任务」时启动：

- `git worktree add worktrees/<task> -b agent/<task>`，每 agent 一目录一分支
- 每个 worktree 独立 `.env`（端口、数据库/Supabase 实例隔离）
- 任务拆分边界从「文件级串行」改为「spec 级并行边界」——一个 spec 一个 worker
- orchestrator 负责 merge 与冲突裁定

**成本警告（实测数据）**：subagent 并行工作流 token 消耗为单线程 2–5 倍，复杂编排可达 5–7 倍；helper agent 可占总用量约 60%。任务粒度 ≤50 行时，并行收益 < 编排开销。

### 2.3 L3 平台选型（仅供未来参考）

| 产品 | 已核实能力 | 适配评估 |
|------|-----------|---------|
| **Qoder Cloud Agents** | `multiagent` 字段支持 `type: "coordinator"`，1–20 个子 Agent 花名册；运行时自动注入 `create_agent` / `send_to_agent` / `list_agents`；Session 隔离容器沙箱；SSE 实时事件流；PAT + REST API 触发；需先创建 Environment（无预置默认） | 技术上完全能实现统一调度。代价：需自写 API 胶水、代码上云端 Environment、模型换为 Qoder 自有（等于放弃现有 Claude review 质量基线） |
| **QoderWake** | GitHub webhook / 定时 / IM @ / 对话四种触发；权限中心（工具·文件·内置工具·模型四维防护）；经验五维沉淀；7×24 无人值守；计算巢一键部署或常驻本机 | 能力最匹配「可离场」诉求。但需常驻机器/云部署，对 9 游戏的个人练习项目属明显过配 |
| **Qoder Desktop 1.0** | 内置 planning / research / coding / review / testing 五类专家 pipeline；跨项目多任务并行 + 统一活动面板 + 自动交付清单；Repo Wiki | 与当前手搭流程高度重合——27 条提交手工实现的东西是其内置能力。代价：换 IDE + 迁移 `AGENTS.md` 的游戏开发约定 |

## 3. 可维护性专项

### 3.1 元规则通胀需设上限

流程维护提交（27）> 功能产出提交（18）。建议硬约束：

> 流程规则总量不超过 150 行；新增一条必须删除一条。

### 3.2 规则源收敛：7 → 2

目标状态：

- `AGENTS.md` —— 规则（唯一）
- `tasks/` —— 实例（一任务一文件）

处理方式：TEMPLATE 内联回任务文件（任务创建时复制为初始态——需防范的是活引用，不是复制）；`CLAUDE.md` 保持薄指针（已达标）；`BACKLOG.md` 可保留或并入 Issues；`/codex-plan-exec` 移入仓库。

### 3.3 缺陷记忆缺口（重要）

现状 `BACKLOG.md` 只登记 P3，**P0/P1 修完即消失**，导致同类缺陷反复出现。

已观察到的证据：`cb8f175 fix: WhackAMoleView CSS 语法修复（补上 .start-btn:hover 闭合 brace）` —— 与其他项目中出现过的「CSS 块未闭合」属同一根因家族。

建议增设 `docs/ai-workflow/PITFALLS.md`（或 `.workbuddy/memory/pitfalls.jsonl`），只记 P0/P1 的**根因签名**（剥离路径行号后的稳定标识 + 技术栈指纹 + 修法），开工时按技术栈指纹召回注入。

## 4. 质量红线：review 不可被自动化掉

自动化的正确边界是：**搬运自动化，判断留给人。**

行业已知失效模式：subagent 团队表面分工，实为同一模型在同一上下文自问自答，review 退化为走过场，token 翻倍而质量无提升。

因此无论演进到哪一层，以下为硬约束：

- reviewer 必须**工具级只读**（`tools: Read, Grep, Glob`），物理上无法改文件
- reviewer 与 implementer 不得共享上下文
- P0/P1 的最终裁定权保留在人（或独立 reviewer）手中

当前靠「人 + 角色分离」实现，未来须靠「配置 + 工具权限」实现。

## 5. 结论

**不建议现在引入调度平台。**

1. 平台解决的是「N 个 Agent 争抢资源」，当前痛点是「2 个 Agent 之间人肉搬运」——两个不同问题
2. 当前任务粒度（micro ≤50 行）下，并行收益低于编排开销与 token 成本
3. 已有 37.5% 的流程税，引入平台会进一步放大元开销

**推荐动作序列**：

1. **本周可做（低风险）**：L1 中的 state.json + tasks/ 一任务一文件 + 命令进仓库 三项（约 1.7h）。它们降低流程仪式税（消灭 27 条清空/回填提交），但**不解决**两个人工搬运节点——那需要 L2/L3。原 L1-P0「直调 CLI 拿走 80% 痛点」已撤回（见 §2.1.1）。
2. **同期**：流程减法——规则源 7 → 2，设 150 行上限，增设 PITFALLS 记录
3. **观察**：出现「同时推进 ≥2 个互不依赖任务」时再评估 L2
4. **重估点**：稳定出现 ≥3 个并行任务，或希望 GitHub Issue 触发无人值守修复时，再评估 Qoder Cloud Agents（自建编排）或 Qoder Desktop（换生态换内置 pipeline）

**终局表态**：对单仓库、双 Agent 的个人项目，L1 + 人肉传话很可能就是长期均衡——搬运成本是「判断留给人」红线的结构性价格，不是必须消灭的缺陷。
